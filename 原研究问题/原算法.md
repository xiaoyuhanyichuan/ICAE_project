# 算法执行过程说明

## Update: Infeasibility Handling Flow

The current candidate-evaluation flow now contains two infeasibility layers:

1. Pre-MILP screening: `FeasibilityOracle` checks the topology envelope and the `CDU -> HP+CRAC -> Chiller -> Tower` capacity chain before the inner MILP.
2. Pre-MILP projection repair: when allowed by configuration, the Oracle may project `Cap_CDU`, `Cap_HP`, `Delta Cap_Tower`, and `n_CRAC_remove`.
3. Formal inner MILP: feasible candidates still enter `InnerDispatchMILP` as before.
4. Post-MILP diagnosis: if the formal MILP is infeasible or `INF_OR_UNBD`, `evaluate_solution()` can rerun a diagnostic model with `DualReductions=0`.
5. Diagnostic relaxation: if infeasibility is confirmed, the code can enlarge diagnostic slack bounds and summarize CDU, CRAC, Chiller, Tower, Power, Heat, and SOC slack.
6. Mapped repair and one retry: CDU/CRAC/Tower slack can be mapped back to existing outer variables and the formal MILP is resolved once. Chiller slack is diagnosed but not automatically repaired because the current planning layer has no chiller-expansion decision variable.
7. Infeasible memory: repeated candidates in the same infeasible topology/capacity/reason bucket can be skipped with a penalty.

This is an engineering evaluation strategy. It does not modify the physical equations documented in `source_md/modelexplanation.md`.

本文档面向当前 `Myproject` 代码实现，详细说明整个求解流程如何运行，包括：

## pymoo convergence analysis addendum

When `solver.outer_engine = "pymoo"` and `solver.convergence.enabled = true`, the outer-loop callback records each generation's current population objectives after pymoo updates `algorithm.pop`.

The convergence post-processing is diagnostic only and does not change the optimization model, constraints, objective functions, candidate evaluation, or selection logic. It writes:

- [results/convergence/pymoo_generation_population.csv](/d:/Myproject/results/convergence/pymoo_generation_population.csv): generation-level population objective snapshots.
- [results/convergence/pymoo_convergence_metrics.csv](/d:/Myproject/results/convergence/pymoo_convergence_metrics.csv): Hypervolume, IGD+, and generation-to-generation improvement metrics.
- `results/figures/pymoo_convergence_hv.png`
- `results/figures/pymoo_convergence_igd_plus.png`
- `results/figures/pymoo_convergence_summary.png`

Metric conventions:

- Only feasible and finite objective points are used for HV / IGD+.
- `TLCC` and `TCE` are min-max normalized using all feasible points observed in the current pymoo run.
- Hypervolume uses the normalized reference point from `solver.convergence.hv_ref_point`, default `[1.1, 1.1]`.
- IGD+ uses the non-dominated set from all feasible points observed during the current pymoo run as the approximate reference front.
- The recommended generation is a diagnostic suggestion based on a consecutive low-improvement window; it is not a proof of global convergence.

## 1. 总体框架

当前项目采用的是一个典型的**双层优化/评估框架**：

1. **外层规划层**  
   使用 `NSGA-II` 搜索结构规划决策：
   - 哪些机柜做液冷改造
   - 哪些设备组接入液冷
   - 拆除多少 CRAC
   - CDU / HP / TES / BESS / Tower / HX 装机容量多大

2. **内层运行层**  
   对于外层给出的每一个候选规划解，建立并求解一个 `MILP` 运行调度模型，评估该规划方案在全年典型日场景下的：
   - 运行成本
   - 运行碳排
   - 热量流分配
   - 电力平衡
   - 设备运行可行性

3. **目标回传外层**  
   内层调度结果再与外层的投资、固定运维、隐含碳、结构罚项等合并，形成：
   - `TLCC`
   - `TCE`

4. **外层据此继续进化**  
   `NSGA-II` 用回传的双目标值对种群进行非支配排序、拥挤度计算、选择、交叉、变异，逐代逼近 Pareto 前沿。

因此，这个项目不是“先建一个大一体化 MINLP 直接求”，而是：

> 外层做长期规划搜索，内层做短期运行评估，内层评估结果反哺外层。

## 4. 典型日降维

## 4.1 为什么要做典型日

如果直接把全年 `8760h` 全部放进每一次内层调度 MILP，那么外层每评估一个候选解都要解一个很大的优化问题，计算量会非常高。

因此当前实现采用：

> 用少量“典型日”代表全年运行场景，再用权重还原到全年。

- [src/model.py:474](/d:/Myproject/src/model.py:474)
- [src/typical_days.py](/d:/Myproject/src/typical_days.py)

## 4.3 典型日构建逻辑

当前 `TypicalDayBuilder` 默认做：

- `4` 个季节典型日
- `1` 个峰值日（可选）

见 [src/typical_days.py:24](/d:/Myproject/src/typical_days.py:24)。

### 4.3.1 日特征

先把全年时序按天重塑为：

$$
n_{days} \times 24
$$

然后使用如下列构造每日特征：

- `price_grid`
- `cf_grid`
- `heat_demand_kw`
- `it_total_kw`
- 机柜负荷统计特征：`rack p10 / p50 / p90 / std`
- `t_wb`

这些特征由 `rack_it_*_kw` 逐日派生，用于保持典型日选择对机柜异构负荷形态敏感。

### 4.3.2 季节 medoid 选择

按冬春夏秋分季后，每个季节不做复杂聚类，而是选取一个**最接近季节中心的代表日**：

$$
d^* = \arg\min_d \|x_d - \bar{x}_{season}\|^2
$$

见 [src/typical_days.py:33](/d:/Myproject/src/typical_days.py:33)。

### 4.3.3 峰值日附加

为保证容量校核不过于“平均化”，代码会单独找一个峰值日：

$$
Score_d
= \max(HeatDemand_d)
 + 0.2 \cdot \max(IT^{total}_d)
$$

得分最高的那天作为 `peak_day`，见 [src/typical_days.py:108](/d:/Myproject/src/typical_days.py:108) 到 [src/typical_days.py:114](/d:/Myproject/src/typical_days.py:114)。

### 4.3.4 权重还原全年

每个典型日会带一个 `weights_days[k]`，表示它代表全年多少天。  
最终会归一化，使总和约等于：

$$
\sum_k w_k \approx 365
$$

见 [src/typical_days.py:132](/d:/Myproject/src/typical_days.py:132) 到 [src/typical_days.py:143](/d:/Myproject/src/typical_days.py:143)。

## 4.4 典型日对内层目标的作用

内层目标和年运行统计不是简单求 24 小时合计，而是：

$$
\sum_k w_k \sum_t (\cdot)
$$

因此运行成本、运行碳排、购电量、供热量最终都被还原为**全年量级**。

## 5.2 NSGA-II 进化流程

代码位置：

- [src/nsga2.py](/d:/Myproject/src/nsga2.py)

当前 NSGA-II 的执行逻辑如下：

1. **初始化种群**

在上下界内随机生成 `population_size` 个连续向量：

$$
x^{(0)} \sim U(lb, ub)
$$

2. **解码**

对每个向量进行边界裁剪和整数化：

- 二进制变量 `round -> clip`
- 整数变量 `round`
- 连续容量变量 `clip`

3. **个体评估**

调用 `eval_fn(x)`，本质上就是 [src/model.py:488](/d:/Myproject/src/model.py:488) 的 `evaluate_solution()`

4. **非支配排序**

用 `TLCC` 和 `TCE` 做双目标非支配排序，见 [src/nsga2.py:53](/d:/Myproject/src/nsga2.py:53)

5. **拥挤度计算**

在同一前沿内部计算 crowding distance，见 [src/nsga2.py:76](/d:/Myproject/src/nsga2.py:76)

6. **锦标赛选择**

优先选：
- rank 小
- rank 相同时 crowding 大

7. **交叉**

- 连续/整数变量：`SBX crossover`
- 二进制变量：均匀交叉

8. **变异**

- 连续/整数变量：`polynomial mutation`
- 二进制变量：bit-flip

9. **父代 + 子代合并**

再做一次非支配排序，保留前 `population_size` 个个体进入下一代。

10. **最终输出**

只返回最终种群中的第 `0` 前沿：

$$
Pareto = Front_0^{final}
$$

见 [src/nsga2.py:316](/d:/Myproject/src/nsga2.py:316) 到 [src/nsga2.py:320](/d:/Myproject/src/nsga2.py:320)。

## 5.3 外层的可行性优先规则

`NSGA-II` 的支配关系不是单纯比较 `f1/f2`，而是先比较可行性。

见 [src/nsga2.py:39](/d:/Myproject/src/nsga2.py:39)。

规则是：

1. 可行解总是优于不可行解
2. 两个都不可行时，约束违约小者更优
3. 两个都可行时，再按 `TLCC/TCE` 比较支配关系

因此外层搜索并不是“盲目只看目标”，而是：

> 先尽量留住可行解，再在可行解之间做成本-碳排权衡。

## 7. 两层如何耦合

## 7.1 外层给内层什么

外层把以下固定规划决策交给内层：

- 机柜液冷改造拓扑 `y`
- 设备组液冷适配 `x_ig`
- CRAC 拆除数量
- `CDU / HP / TES / BESS / Tower / HX` 规划容量

在代码中，它们被封装为：

- `FixedPlanningDecision`

内层把这些视为常数，不再优化。

## 7.2 内层回给外层什么

内层回传的是给定规划解的最优运行结果：

$$
C_{op}^{annual},\quad CO2_{op}^{annual}
$$

以及一系列运行可行性和设备利用诊断。

## 7.3 外层如何把运行层结果并入总目标

代码位置：

- [src/model.py:707](/d:/Myproject/src/model.py:707) 到 [src/model.py:741](/d:/Myproject/src/model.py:741)

把：

- CDU
- HP
- TES
- Tower
- HX
- BESS 功率侧

全部用 `CRF` 折算成年度投资。

### 7.3.2 年固定运维

### 7.3.4 与内层运行结果耦合

最后形成：

$$
TLCC
= C_{capex}^{annual}
 + C_{fom}^{annual}
 + C_{op}^{annual}
 + Penalty
$$

$$
TCE
= EI^{annual}
 + CO2_{op}^{annual}
 + Penalty
$$

所以，外层不是直接优化内层变量，而是通过：

> “给内层一个规划结构”  
> “由内层算出这个结构的最佳运行表现”  
> “再把运行表现折回外层目标”

来实现双层耦合。

## 8. 罚项与可行性逻辑

## 8.1 为什么外层不全是硬约束

也就是说，部分约束不是直接把解剔除，而是通过大罚项推高 `TLCC/TCE`。

如果 `two_stage.enabled = true`，则外层会分两阶段：

用较宽边界和一组参数先粗搜：

$$
Pareto^{(1)}
$$

### 阶段 2

根据第一阶段 Pareto 解的变量范围，把边界缩窄：

$$
Bounds^{(2)} = \text{Narrow}(Bounds,\; Pareto^{(1)})
$$

再在缩窄后的空间做第二次搜索。

这样做的作用是：

- 第一阶段负责找大致可行区域
- 第二阶段负责在较优区域内加密搜索

## 12. 一条候选解的完整生命周期

用一句更直观的话把整个双层流程串起来，可以写成：

1. `NSGA-II` 随机/进化得到一个外层候选规划向量 `x`
2. `evaluate_solution(x)` 把它解码为：
   - 液冷改造拓扑
   - CRAC 拆除台数
   - 各类设备容量
3. `FeasibilityOracle` 先做快速工程可行性筛查与必要投影
4. 若可继续，则构造 `InnerDispatchMILP`
5. 内层 `MILP` 在典型日场景上求最佳运行调度
6. 返回年度运行成本、年度运行碳排、运行可行性指标
7. 外层再加上投资、固定运维、隐含碳、结构罚项，得到 `TLCC/TCE`
8. `NSGA-II` 根据这两个目标值决定这个规划方案在种群中的优劣
9. 多代重复后形成最终 Pareto 前沿

## 13. 审核建议

如果你要从算法正确性的角度审核整个项目，我建议优先检查这几条主链是否和你的理论一致：

1. **典型日降维是否保留了你关心的峰值与季节性**
2. **外层变量是否覆盖了你要做的长期规划决策**
3. **Oracle 是否过度投影，改变了外层原本的设计自由度**
4. **内层热平衡、TES、热泵、塔侧链路是否与你当前文档一致**
5. **TLCC/TCE 是否都按你想要的“年度口径”或“寿命口径”汇总**
6. **罚项类约束是否应该升级为硬约束**

## 14. 总结

当前代码实现的本质可以概括为：

> 先用典型日把全年运行压缩成少量代表场景，  
> 再用外层 `NSGA-II` 搜索长期改造规划，  
> 对每个候选规划都调用一次内层 `MILP` 做最优运行调度评估，  
> 最后把运行层结果回传给外层，形成成本-碳排双目标的 Pareto 优化。

这就是该项目“规划层 - 运行层”双层耦合的核心执行逻辑。
